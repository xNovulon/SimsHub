CORRECTIONS: I found nothing that refutes the core model. What a builder should believe:

1. **Load order and conflict winners.** Within one Priority, packages load in a depth-first FindFirstFileW walk: NTFS upper-cased ordinal order, with folders entered at the point their name comes up. When two copies of a key conflict, the first-loaded one wins. This rule was proven in-game only for XML tuning, on Windows, in 2017. Before shipping anything that decides CC winners, re-test it on 1.126 with two conflicting CAS parts; it takes minutes.

2. **Priority.** A higher Priority beats a lower one. A more specific pattern (fewer wildcard folder segments) takes over a file from the default `*/*.package` lines regardless of line order.

3. **Folder names.** `_` sorts after letters and digits but is not strictly last: backtick, `{`, `~` and non-ASCII names come after it.

4. **Resource.cfg profiles.** The only empirical proof that folders not matched by patterns are skipped is the depth limit ("5 folders deep"). Name-based skipping and `...` are supported by static reading only, so test in-game before relying on them. A Resource.cfg profile never disables script mods. Scripts load from the Mods root and first-level folders whatever Resource.cfg says, so a profile that hides a folder of packages can leave its script loaded without its companion package. Handle scripts by moving them, never by cfg.

5. **Nested Resource.cfg.** Treat nested Resource.cfg files as live (unconfirmed, but the safe assumption). The tool should flag stray ones and never write one inside subfolders. There are none today.

6. **Merged package size.** Keep merged packages below 2^31 bytes including the index. Game support above 2 GiB rests on static reading only, and 125.package does not test it. Other tools may use signed 32-bit offsets. The S4S 2 GB cap is lore; the cited S4S thread does not say it.

7. **Junctions.** Do not rely on junctions. The claim that no link-resolving API is imported is wrong: GetFinalPathNameByHandleW is imported and used, in a helper that finds a path's real drive letter (0x12a61d0). The cause of the 2026 reports is still unknown. The exe here also imports a non-EA DLL ('anadius64'), so EA-app user reports may not transfer. Hard links on the same NTFS volume are safe, but only on C:. Beware of tools that edit files in place.

8. **Library cleanup.** Exclude `Mods_parked\_old_caches` from any restore or merge, because its thumbnail-cache .package would load as a mod. Report "conflicts" by uncompressed size (16,647) or by content hash, not by (fsize, msize) (19,029). Keep one NSW lighting variant, not 20.

**The library index is out of date.** Files have moved since library.sqlite was built. For example, Mods/animation/anim1.package is gone and research/merging/s4s_manifest.py --selftest now crashes. Tools must look up each package by root, then the other root, and check the size (see research/merging_review2/resolve.py). Better still, rebuild the index before any merge.

**The manifest format and unmerge rules are safe to build on.**
- Format: u32 version, then the recursive folder / package / (instance, type, group) layout.
- Write one manifest per package, key 7FB6AD8A:0:0, zlib compressed, first in the file. S4S does not check the version and does not care about its position or compression.
- Every resource must be listed under exactly the name you want back.
- Names within a folder must be unique ignoring case. S4S compares names case-sensitively but writes files with File.Create, so 'X' and 'x' become one file.
- Names must be sanitised: no path separators, no '..', no drive letters. S4S builds output paths with Path.Combine and would write outside the target folder.
- Never put any other resource of type 0x7FB6AD8A into a package. S4S treats any resource of that type as the manifest, and a bad one makes it refuse the package.

**S4S merge behaviour.**
- For a key in several sources, the first copy is kept but every source still lists it. Unmerging then gives each source the winner's bytes, so the losing originals cannot be recovered.
- Duplicate keys inside one source are all written.
- There is no filtering by resource type. Source manifests are skipped only because their key clashes with the new one.
- The 2 GB check only runs when merging. Opening and unmerging have no size limit.

**Unmerge loss in the existing 165 merged packs:**

| Lose only S4S's batch-fix history record (0x6BF15BBE) | 125 |

The dropped content is mostly animation clip headers and clips, plus 1,726 textures converted from RLE2 to LRLE after merging.

**Which duplicate wins in-game.** The best evidence (scumbumbo, tested in-game in 2017) says the first-loaded copy wins, and the project's winners.py already assumes this. It is still unconfirmed on game version 1.126. Keep excluding or isolating packages whose copies differ, because merging moves every resource to the merged file's position in the load order.

**Startup cost per file is underestimated.** 0.13-0.59 ms/file is the best case for raw file reads. I measured about 8 ms/file when Windows Defender (or something like it) scans a file on first open, and 10 ms/file on one cold pass over older files. The Steam test implies about 9 ms/file in-game even on a warm second run. Use 0.5-10 ms/file (roughly 0.3-6 s for this 624-file library), not a fixed 0.2 s.

**EA's 5,080 packages** include 4,035 string-table packages in 18 languages, loaded by a wildcard in Resource.cfg. Whether the game opens all of them is unverified, so comparisons of mod file count against EA file count are weak.

**Size cap.** To stay within what EA itself ships, keep merged packs at or below about 1.98e9 bytes (1.85 GiB), not 1.9 GiB. CORRECTIONS: What a builder should believe instead (all measured read-only on this machine on 2026-09-24):

1. Package indexes are not the problem. Reading all 624 indexes takes 0.06-0.34 s.

2. CAS parts probably drive startup cost, and the cause is layout rather than CPU work. S4S-merged packages scatter the 755,662 CASPs among textures; 8 sample packages spread 49k CASPs over 15.1 GB. Each CASP is therefore a separate random read. With 15.7 GB RAM and 0.3-0.6 GB free, the OS cache does not keep them between launches.
   - Reading them all took 249 s single-threaded and 29 s with 8 threads in plain Python. So the 265 s/102 s 'lower bound' in claim 4 is wrong.
   - EA keeps CASP, OBJD, COBJ and SimData together in small SimulationPreload packages (53 MB base).
   - So a load-time merger should do more than cut file count. It should place catalog resources (CASP, OBJD, COBJ, SimData, tuning) contiguously, ideally in a separate small 'preload' package, keep textures and meshes apart, and stay under 2^31 bytes per file.
   - Whether the game actually reads every CC CASP at startup is still unproven. It needs one timed launch with a Process Monitor trace.

3. Corrected counts:
   - Script modules: 2,246 importable .pyc (not 2,256). The game __imports__ every .pyc/.pyo in every ts4script; loose .py files are not imported.
   - XML: 26,359 resources (259.1 MB), but about 507 are ASM animation state machines, not tuning. sim/68 holds 5,367.
   - lastException (Jul 31): 26 UnavailablePackSafeResourceError, not 13; 63 resolver.py:123 AttributeErrors; about 2 reports per minute. The current lean set logs 3 per session. 'Error spam lags this setup' is unproven.
   - 4K CC textures cover about 52% of CC RLE2 and 77% of LRLE, not all CC. They are whole-resource zlib, so the full 4096 data is read and inflated even when only 2048 is used.

4. Graphics override: the Simp4Sims 2021 override is the only SGR parsed and does disable Sim LOD, object LOD bias and size culling. However, options it lacks (LuckEnabled, StoryProgressionEffects, ColorAssist and others) are still registered by the exe. Missing props such as FreePhysicalMemoryThresholdMB (stock value 100) fall back to unknown exe defaults. TextureSizeThreshold does nothing at objectquality High (DropTexMipsOnLoad=0), and FSAA 512 is probably clamped. The FPS and VRAM effects are unmeasured.

Existing tools the survey missed: CCMerger (LazyDuchess, open source, size and file-count caps, known fence and invisible-object breakage), s4pi-reforged (Rust, threaded CLI merge/unmerge with conflict detection, S4S-compatible) and Better Exceptions' on-demand Conflict Detector. None advertises load-time layout optimisation.
